# Tuxherd Workspace Capability and MAM

**Status:** Proposed design supplement · **Date:** 2026-10-26

This supplements [DESIGN.md](../DESIGN.md), especially its work/personal separation, trust boundaries, TRP profiles and roadmap. It proposes extensions, not shipped functionality. The TRP-Workspace 2.0 proposal below explicitly supersedes the workspace profile definition in DESIGN §11.1; other base-design rules continue to apply unless stated here.

## Purpose and limits

Tuxherd should support mobile application management without device enrollment (MAM-WE) as **T0: Unenrolled Workspace**. A tenant manages its apps, identity and encrypted work data on a personal Linux host without acquiring authority over that host. Signed OCI workspaces also provide an app delivery option inside enrolled T1 BYOD and T2 corporate environments; DESIGN §7.2's AppStream, Flatpak and native delivery remain available.

The core rule is: **everything the tenant ships is a digest; everything the user creates is ciphertext; everything else is temporary.** Ciphertext means persistent user data; working plaintext necessarily exists while unlocked. Persistence exceptions are public registration metadata, verified image caches, wrapped offline-scope DEK/lease blobs, epoch and lease counters, the audit chain head and the workspace-instance key (or its wrapped form). Online-scope leases and their DEK envelopes are memory-only. These exceptions must not contain plaintext work content or tokens.

T0 protects against loss of a locked device, offboarding and honest-user mistakes. A separate UID resists non-root personal-session malware reading workspace storage, sockets and process memory. When workspace windows are shown by the personal user's compositor, personal-session code that compromises the compositor can capture workspace pixels and input. That applies especially when the personal user is an administrator: malware can also capture sudo/polkit credentials and become root. T0 does **not** protect against a hostile device owner, root or compromised host. Containers share the host kernel; immutability does not change that boundary.

**Decision:** ordinary internal data may use the bridged model if tenant policy accepts those risks. DESIGN §9.2's separate seat session with its own compositor is the stronger option and is **REQUIRED for anything above ordinary internal on T0**, subject to the absolute exclusions below. It still shares the host kernel and does not resist root. Bridged local unlock SHOULD use FIDO2 user presence (`hmac-secret`) rather than a PIN/password typed into a workspace window; user presence does not attest the compositor or prevent abuse during unlock.

**T0 is never appropriate for admin consoles, production credentials, high-classification secrets, or policy-designated restricted resources** such as payment-card secrets, clinical record repositories or export-controlled designs. These require a separately approved enrolled/managed environment or remote access architecture; enrollment alone is insufficient. “Regulated” is not a blanket exclusion: ordinary mail can contain GDPR-covered personal data. Data classes are assigned by policy per app/resource/audience, not by an enforcement point guessing content. Above-ordinary classes that are not excluded still need an explicit policy, separate seat and suitable assurance; this supplement grants none by default.

The proposed delivery options below reduce which secrets reach the host; they do not raise this live-data ceiling. A remote-access architecture for a forbidden class must separately approve the endpoint and input/output risks too. Calling a T0 viewer “VDI” is not that approval.

## Authority, capability and evidence

Tiers describe tenant authority, capabilities describe available mechanisms, and assurance describes evidence. **Capability is not assurance.** Installing support proves neither integrity nor correct operation. DESIGN §2 defines the authority tiers; §5.1 defines the evidence vocabulary. T1/T2 workspaces report workspace `assurance` independently of any device `trust_level`.

| Capability configuration | Available mechanism | Runtime claim limit |
|---|---|---|
| No distro workspace feature | Distro- or project-signed rootless OCI launcher, never tenant-supplied; encrypted storage where prerequisites exist, typically under the personal UID | `separation: none`; lowest-risk sessions only, no managed display/printing claim. Tenant processes MUST NOT run as container UID 0 (which maps to the personal UID in this mode). Unsupported prerequisites prevent launch. |
| TRP-Workspace 2.0 support installed | Owner-authorized work-user helper, filtering bridge, managed printing and lifecycle integration | May report UID separation and managed boundaries after local checks; installation alone remains unattested. |
| Support plus verified measured immutable host | Same mechanisms plus consented evidence against independently trusted references | Narrow at-rest/freshness decisions and offline leases only within a continuous awake interval; every suspend/resume requires online renewal. No runtime-integrity or higher-class live-access guarantee. |

| Authority tier | Ownership / scope | Permitted evidence axis |
|---|---|---|
| T0: Unenrolled Workspace | No device enrollment; workspace-only authority | `assurance: workspace-unattested` or `workspace-measured-host`; no device `trust_level` claim |
| T1: Enrolled BYOD | `ownership: byod`; read-only allowlisted device posture and workspace-only actions, including posture-only BYOD without a work user | Device `trust_level: software / tpm-key / tpm-measured`; workspace `assurance` separately if a workspace exists |
| T2: Corporate | `ownership: corporate`; host management within the agreed ceiling | Same evidence vocabularies, separately evaluated; enrollment never implies measurement |

T0 registers a workspace-instance key bound to the user's IdP identity, not a device certificate. The protocol-fixed maximum permits only its workspace policy, status and `workspace.lock`, `workspace.wipe`, `workspace.revoke-keys`, `workspace.refresh`. There is no tenant root agent, arbitrary host query/script channel, device lock or device wipe.

Before registration, a T0 consent screen MUST list tenant-shipped code, tunnel/destination access and owner-side network exceptions, storage quota, allowed commands, the published report schema and every reported verdict, evidence anchoring (including external root publication and tenant record retention/erasure rules), and any watermarking. Evidence and the anonymous host-device-tenant signal require separate consent. Notify before workspace actions (emergency wipe notifies at execution); show all actions locally. The user can remove a workspace at any time, after a data-loss warning, and registration is retired. Removal of one definition must not delete siblings sharing its work user.

Evidence consent withdrawal removes the evidence claim and triggers policy re-evaluation, **not wipe**. Revoke any affected offline lease server-side; the instance where consent is withdrawn locks immediately even offline. Other connected cooperative instances lock when notified; disconnected copies remain bounded by their existing expiry. Keep cached data encrypted without deletion and deny renewal until policy is satisfied. No urgent offline revocation guarantee is implied.

## TRP-Workspace 2.0

**Decision and supersession:** TRP-Workspace 2.0 replaces the TRP-Workspace definition in DESIGN §11.1 and its 1.0 workspace checklist. It requires **TRP-Core packaging/OS-release items only** (C-PKG-01–03 and C-OSR-01–02), not the full Core profile, Desktop profile or an enrolled agent. TRP-Core is a release conformance profile; device enrollment is a TP/1 operation. Packages may exist with the agent disabled.

`systemd-homed` with LUKS2 **SHOULD** be used; fscrypt is permitted at reduced assurance with weaker metadata protection disclosed and lifecycle tests required. This deliberately relaxes base W-HOM-01's MUST for distro adoptability. Neither backend alone supplies remote tenant-key revocation; use the separate tenant-keyed volume described below.

The owner installs and updates distro packages. A polkit-gated setup may require root to allocate users/resources; distro services retain only narrowly scoped privileges under owner control. Tenant code receives no such authority.

| Contract area | Required behavior for the corresponding capability |
|---|---|
| User and storage lifecycle | One Unix user per **(local human user, resource tenant)**, not a machine-wide user shared by humans. Multiple workspace definitions for that pair may share the user but have separate instance keys, volumes and storage paths. Use homed preferably or disclosed fscrypt fallback; enforce quota and scoped removal. |
| Session activation and lock | For bridged sessions, an owner-side helper obtains the local unlock secret/user presence, activates the encrypted home and starts `user@UID` without seat login. Lingering is not an unlock mechanism. In bridged mode, personal-session lock/logout locks all dependent workspaces; in separate-seat mode use work-session lock/logout. Suspend and owner-wide lock affect all workspaces. Idle timeout, lease expiry and instance commands lock only the affected instance: stop its apps, unmount its volume and drop its keys; stop the work user manager and deactivate the home only when no sibling instance remains active. Refuse unlock if safe swap/hibernation is unavailable. |
| Rootless runtime and subid | Tested Podman/runtime, cgroup v2 delegation, isolated storage and network namespace. Allocate nonoverlapping subuid/subgid ranges through supported NSS subid or a predeclared fixed tenant-slot pool; never depend on ad hoc entries surviving host activation. |
| Owner-side network/privacy floor | Deny LAN, link-local (including mDNS) and host-loopback egress outside the tenant tunnel by default, including `host.containers.internal` aliases, IPv4/IPv6 and direct printer routes. Only the owner may grant explicit local exceptions; tenant `NetworkPolicy` cannot weaken the floor. Mask host-sensitive `/sys` (DMI, device/topology identifiers) and `/proc` (host processes, mounts and network state); expose only runtime-required views. |
| Desktop bridge and portals | In bridged mode, dedicated bridge UID, distinct from personal and work UIDs and not ptraceable by them; narrow authenticated per-instance sockets. Workspace-side portal backend runs as the work UID in its isolated bus/namespace and talks only to this bridge. No personal session bus or unrestricted host sockets. Protocol-global/version allowlist and deny tests below are mandatory. |
| Device-access broker | Owner-controlled, per-request grants for PipeWire audio/camera, FIDO hidraw and PC/SC smart cards; no broad uaccess ACL or raw host PipeWire socket for the work UID. Deny screencast nodes unless policy explicitly permits them. Broker IME/input methods and redact notifications; do not share personal input-method services or notification content by default. |
| Accessibility | Isolated workspace AT-SPI bus; no personal accessibility bus or cross-boundary text/input access. Any accessible bridge path needs explicit owner consent, policy and a tested restricted API. |
| Printing | Workspace PDF/virtual printer; preview/export policy; approved forwarding means IPPS to a tenant print service **through the workspace tunnel**. No host CUPS/socket/spool or raw printer devices. `printing: managed` also requires the egress floor to block direct printer bypass; an owner exception enabling bypass makes it unavailable. |
| Key and identity lifecycle | Mount/unmount tenant volume, memory-only working keys, FIDO2 user-presence unlock recommended, isolated identity broker and lease expiry handling. |
| Host ABI | Versioned `workspace-host-abi` for compositor, portals, runtime, networking, GPU and these brokers. Inspect injected GPU libraries locally; report only compatibility verdict, never library inventory. |

TRP-Attested, **not TRP-Workspace 2.0**, owns the optional evidence/TPM broker (A-BRK-01). A T0 host can install it without device enrollment, with separate evidence consent. The work UID receives no `/dev/tpmrm0` or `tss` membership.

A release's `/usr/lib/tuxherd/conformance.json` is a static claim valid for that release's lifetime, with published tests and supported combinations. A per-host runtime report is separate: checks run before launch, lease renewal and after relevant changes. Conformance tests cover denied flows, every denied Wayland global, lock/wipe scope, unsupported configurations, subid collisions and upgrades. In keeping with DESIGN §14.1, optional product features remain profiles; the small, closed capability set below is versioned with ABI 1 and reports runtime availability, not independent feature flags.

## Capability and compliance signals

Local checks may inspect users, services, sockets, namespaces, compositor, print routes and injected libraries, but **MUST NOT send that inventory to T0 tenants**. Publish `workspace-report-v1` on the consent screen. Its closed schema contains only tenant/workspace/user identifiers, image/policy digests, evaluation/expiry times, tier, assurance, ABI level, the fixed capability verdicts below, and per-claim source (`workspace-self`, `host-helper` [unattested], `host-tpm`, `server`), opaque evidence reference and verifier result (`accepted`, `rejected`, `unavailable`). Evidence references must not encode host identifiers. Identifiers, digests and opaque references use constrained formats; no arbitrary diagnostic strings, extensions or host inventory fields are allowed.

| Fixed verdict / ABI field | Meaning and verification limit |
|---|---|
| `separation: none / uid / unavailable` | Distinct work UID, isolated storage and sockets required for `uid`. Same-UID containers, Toolbox/Distrobox or personal-home/session-bus sharing cannot claim it. |
| `display_boundary: unmanaged / managed / unavailable` | Active display/portal paths use the filtering bridge or an isolated seat compositor with equivalent portal/flow restrictions. In bridged mode this **does not resist personal-session compromise of the compositor**. |
| `display_mode: same-uid / bridged / separate-seat / unavailable` | Fixed local configuration verdict, used with `display_boundary` to require the separate-seat model; at unattested assurance it is not proof against owner tampering. |
| `printing: unmanaged / managed / unavailable` | Managed path plus blocked direct printer/spool/network access within the supported boundary. |
| `host_evidence: unverified / measured / unavailable` | Fresh evidence accepted against named reference policies, with scope recorded by the verifier; no mutable runtime attestation. |
| `workspace_abi: 0 / 1` | `1` means **runtime self-check reported ABI 1**, not verified integrity or merely a package declaration; `0` means unavailable/failed. |
| `workspace_integrity: unverified / digest-pinned / unavailable` | Accepted image/signature/policy versions pinned; actual execution remains a cooperative claim against host root. |
| `gpu_compatibility: compatible / incompatible / unavailable` | Local ABI check only; no host library names, versions or paths transmitted. |
| `host_device_tenant: none / read-only / root-capable / undisclosed` | Separately consented anonymous host-authority signal; no device-tenant name. `undisclosed` cannot satisfy a requirement for `none` or `read-only`. |

`assurance: workspace-unattested / workspace-measured-host` is the workspace-subject counterpart of device `trust_level`, not an equivalent enrolled-device `tpm-measured` evidence level. On unattested hosts, requirements are **configuration-correctness gates against accidents and honest misconfiguration, not controls against a dishonest owner**. Missing/stale/failed checks block the affected launch/renewal or permit only an explicitly authorized lower class; never silently substitute an unfiltered path. Hosts without a TPM cap at `workspace-unattested`. This is a supported configuration, not a non-conformance.

Evidence reports prefer nonce-bound quotes and signed PCR 11 / pcrlock policy verification without raw event logs. This version **does not transmit raw event logs**; unsupported verification yields `unavailable`. Local log parsing must not leak firmware versions, paths, db/MOK certificates or serial-bearing identifiers. Per-tenant AKs reduce correlation, but EK handling at a verifier can still correlate hosts; disclose verifier exposure/retention on the consent screen. No anonymity guarantee is implied.

### IdP and SSF enforcement

**T0 workspace subjects MUST NOT be emitted as `device-compliance-change` or as an SSF `device` subject.** Use a proposed SSF complex subject with `user: {format: iss_sub, iss: <IdP issuer>, sub: <user subject>}` and a non-`device` member `urn:tuxherd:workspace: {format: opaque, id: urn:tuxherd:workspace:<id>}`. Signed SETs carry proposed namespaced events `urn:tuxherd:event:workspace-posture-change` (fixed verdicts, assurance and expiry) and `urn:tuxherd:event:workspace-revoked`; user/session revocation may additionally use CAEP `session-revoked` for the explicitly bound session. These workspace events require a Tuxherd-aware receiver; they are not generic CAEP device compliance.

A Tuxherd-aware IdP authenticator (e.g. the DESIGN §6.4 Keycloak integration) MUST require proof of the registered workspace key plus a short-lived, audience-bound posture token signed by the verifier/key broker. IdP rules must restrict each covered app/resource/audience's tokens to eligible registered workspace keys, and deny a host-browser flow without that proof. **Without those rules, host-browser access bypasses T0 data policy.** Registration proves identity and possession of a registered key, **not an approved client**; a dishonest owner can register or emulate software. DPoP binds supported OAuth tokens, while managed-browser SaaS session cookies remain bearer tokens unless DBSC or a comparable service-side binding is deployed. Key release and session revocation cannot recall copied cookies.

Access enforcement also covers resource servers: mail/file sync, native clients, refresh tokens, app passwords, alternate APIs and existing sessions must not bypass the approved audience/path. Where a SaaS provider cannot enforce this, report that resource as unsupported for the claimed control. SSF delivery is asynchronous: publish maximum token lifetime, authorization-cache age and event-delivery/processing bounds; expire access when required posture is stale. Server revocation denies new grants after the authoritative state change, but already issued tokens and disconnected enforcement points remain bounded by their actual expiry/cache policy. Test loss of SSF, broker partitions and concurrent revoke/renew, not just sign-in denial.

## Policy mapping to data classes

`AssuranceMapping` binds policy-assigned app/resource/audience classes to authority, evidence and capabilities. The IdP gates tokens, the key broker gates decryption leases, and the workspace implements cooperative local flow policy. This is a minimum mapping, not a grant:

| Data class/use | Required capabilities and policy | T0 ceiling |
|---|---|---|
| Public / low-risk SaaS session | Approved app image (server-side in remote mode) and identity policy; `separation: none` permitted; no sensitive local cache | Lowest-risk access, no personal/work isolation claim |
| Ordinary internal mail, chat and documents | `separation: uid`, `display_boundary: managed`, `printing: managed`, ABI 1; deny exports/printing unless allowed; short online lease | Bridged model allowed only with explicit tenant acceptance of compositor/input risk; separate seat recommended |
| Offline cache of the same internal class | Preceding requirements plus measured evidence, acceptable boot/image freshness and TPM-bound lease/counters | Bounded offline lease only within a continuous awake interval; every suspend/resume invalidates it and requires online renewal. No class promotion. Without TPM: unavailable; fallback is online access with memory-only lease |
| Above ordinary internal, excluding forbidden classes | Explicit separately approved policy, separate seat/compositor, required evidence and capabilities | Separate seat REQUIRED; denied until that policy exists |
| Admin consoles, production credentials, high-classification or policy-designated restricted resources | Approved enrolled/managed environment or remote access policy and evidence | **Never T0**, regardless of measurement or separate seat |

`WorkspaceDefinition` pins delivery/ABI; `DataProtectionPolicy` defines clipboard, drag/drop, files, URI, screencast and print flows; `IdentityBinding` defines accounts, DPoP and SSF; `LaunchPolicy` sets re-authentication and capabilities; `NetworkPolicy` sets tunnel/DNS/destinations subject to the owner floor; `KeyPolicy` sets release/rotation/leases. `AuditEvidence` records provenance/outcomes, not host inventory. Unknown classes default to denial.

`AuditEvidence` anchors **server-side events only**: lease issuance, key release, watermark-ID assignment, tunnel document fetches, watermark-key epochs, consent-version hashes and admin actions. Host self-reports (including "screenshot attempted", host facts and local audit-chain heads) are not anchorable evidence: anchoring them proves only that the host said something. This adds no fields to `workspace-report-v1` and grants no host collection authority.

The evidence leaf is `C = H("tuxherd-evidence-v1" ‖ salt ‖ canonical{event_type, event_id, tenant_id, wm_id, lease/render id, user_iss, user_sub, instance-key thumbprint, doc digest, policy hash, wm-key epoch, time, hash of instance-signed request})`. Use a fresh 256-bit random salt per leaf and a fixed, unambiguous canonical encoding with explicit absent values for fields inapplicable to an event. The record and salt stay in access-controlled tenant audit storage; only `C` enters the separate `corp-evidence` log. Only Merkle roots are anchored externally, using DESIGN §10.3's pinned witness policy and pluggable checkpoint anchor interface, with hourly OpenTimestamps by default. For aggregate anchoring, preserve the proof from this log's signed checkpoint to the aggregate root as well as the event inclusion proof. The evidence log has its own retention/privacy rules; devices never need its inclusion proofs. Deleting all retained records, salts and identifying mappings limits later opening/linkage of commitments; it cannot erase investigation bundles already shared or by itself establish a legal erasure outcome.

An investigation bundle contains the salt, record, signed request and registration-key history, inclusion/aggregation proofs, witness co-signed checkpoint, applicable trust policy and completed anchor proof, and is provided to the accused too. Preserve authorized independent copies under that retention policy: roots cannot reconstruct deleted evidence. Track `local-only`, `witnessed` and `anchored` evidence separately. A completed timestamp establishes existence no later than its timestamp, not the event's own clock value; a commit-before-leak claim also needs an independently established later leak bound. Late anchoring cannot backdate an unwitnessed interval. This is **deterrence and forensics, not prevention**; anchoring improves trail integrity, not attribution. Evidence-log outages degrade evidence only, never access; payload-command inclusion requirements remain separate (DESIGN §10.4).

## Proposed delivery options

These options extend `WorkspaceDefinition`; they do not change the settled local OCI contract or existing `workspace-report-v1`. A proposed, separately versioned delivery descriptor selects `local-oci`, `remote-rendered` or `confidential-guest` (research option), with approved artifact/service identity, resource audiences, server channel policy and revocation bounds. Policy evaluates delivery-specific **server/execution evidence separately from host assurance**. Unsupported descriptors fail closed; no automatic switch from remote rendering to document download, or from confidential execution to a normal VM. Consent identifies where apps/data run and the service/verifier's exposure. The execution-evidence schema is **undefined until the research track**: no execution verdicts may be emitted or accepted until a separate versioned closed schema, verifier semantics and consent-screen field list are published. This is not an extension slot in `workspace-report-v1`. No provider is required.

### Remote rendering as a first-class T0 option (proposed)

1. **Register the viewer through the workspace surface.** A bare browser uses a viewer web app at the authenticated tenant discovery origin. Before `POST /sp1/workspaces/register`, it displays the T0 consent screen, including renderer identity/location, retention, allowed server actions, report fields, watermarks and local capture limits; record the accepted consent-version hash. Browser WebCrypto generates the instance signing key locally, with a non-extractable private key retained in origin-scoped browser storage; separate channel keys are generated per connection. The server never generates or delivers the instance private key. IdP authentication and nonce-bound proof register its public key under the same bootstrap/root-continuity rules as a client. Non-extractability is only a browser API restriction, not protection against the owner, same-origin code or a compromised browser; software keys remain copyable at unattested assurance. Storage loss uses the explicit re-registration/recovery flow, retiring the old registration. The browser can report only the closed low-risk verdicts (`workspace-unattested`, `separation: none`, unmanaged display/printing, ABI 0); it cannot claim the client/helper's boundaries. Proposed `POST /sp1/workspaces/<id>/render-sessions` then binds the user/instance, approved app/resource, policy hash, fresh nonce and viewer channel key to a short-lived single-use connection ticket. Consume the ticket atomically against current registration/session authorization; bind reconnects to current authorization and a fresh channel proof. No document DEK or backend application token is delivered to the viewer.
2. **Run the app and identity broker tenant-side.** Use isolated per-user/resource-tenant sessions, signed pinned app images and encrypted server storage; retain application cookies, refresh tokens and document keys there. The remote gateway/renderer is a new TCB with patching, tenant isolation, least-privilege key access and disclosed data location/retention. Backend services must accept only the authorized remote path for remote-only resources, including alternate APIs and legacy authentication. An ordinary reverse proxy that sends HTML/document data or reusable backend credentials to the host is not this mode.
3. **Enforce channels at the trusted end.** Deliver rendered frames, with separately approved audio/accessibility output if needed. Default-deny clipboard, file/drive redirection, downloads, print/PDF forwarding, USB, arbitrary URL launches and other data channels at the gateway and remote app/network boundary. A modified viewer cannot re-enable them. Approved exports use an explicit audited server workflow. Remote printing uses the same tenant-tunnel IPPS rule; never the viewer's host CUPS. Assess accessibility and video-conference needs before claiming support; “pixels only” is not a reason to exclude users or silently open a text channel. [Existing remote-desktop implementations expose these redirection controls](https://guacamole.apache.org/doc/gug/configuring-guacamole.html); their availability alone is not a tested Tuxherd boundary.
4. **Minimize what an authorized session can disclose.** Scope backend permissions, restrict bulk queries/exports and apply server-side rate/concurrency limits. Embed disclosed opaque watermarks before streaming and record render assignments in `AuditEvidence`. A host can still automate browsing, OCR every visible page, inject input or relay the live session. A pixels-only channel is still a data channel; rates bound opportunity, not prevent leakage.
5. **Terminate at the server.** Re-evaluate authorization on connect/reconnect and at a policy-bounded interval. Apply the remote-mode `workspace.lock`, `workspace.revoke-keys` and `workspace.wipe` semantics and signature/audit requirements in “Commands and wipe scope” below; identity revocation can independently terminate sessions and deny reconnect. Publish the worst-case termination delay, including authorization caches and partitions; gateways fail closed when their authorization freshness expires. Local viewer lock is cooperative. Remote offboarding stops future service but cannot delete captured output, and server backups may delay storage shred.

This removes bulk source files and reusable application secrets from the endpoint and makes future-access denial independent of host cooperation. It adds hosting cost, bandwidth/latency, outage sensitivity and server concentration of data; offline work is unavailable. A low-risk browser viewer needs no TRP-Workspace helper but reports local boundaries as unmanaged. **Ordinary internal use still requires the existing UID, managed display/print and ABI 1 viewer contract**, with tenant acceptance of the bridged compositor risk. Above-ordinary use still requires a separate seat and explicit policy, and forbidden T0 classes stay forbidden. Server channel enforcement is an additional control, not a substitute verdict for local separation.

### Confidential remote renderer and local guest watch item (research option)

**Lead with a confidential remote renderer**, which can narrow hosting-operator exposure without a local hardware dependency; tenant/vendor hosting still needs physical security. [AMD SEV-SNP](https://www.amd.com/en/developer/sev.html) and [Intel TDX](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/technical-documentation/tdx-security-research-and-assurance.html) ship on compatible EPYC/Xeon-class workstation/server parts, not assumed ordinary Linux laptops. A normal VM trusts host root; a confidential VM protects approved guest memory and keys from host software only within the vendor threat model. Keep the local confidential guest as a watch item. Our T0 adversary has physical access: cheap DRAM attacks such as [BadRAM-style SPD aliasing](https://badram.eu/) and interposers sit outside vendor TEE threat models but inside ours. Mitigations must be evaluated per platform; a valid quote is not evidence that all such physical attacks are excluded. This adds no hardware requirement to enrollment.

The release protocol for this research option must:

- Generate separate signing/recipient/channel keys **inside the guest**; bind their hashes, a verifier nonce, tenant, instance and policy context into attestation report data. Verify vendor endorsement chains, security/revocation collateral, debug-disabled state, migration policy and tenant-approved boot measurements. Bind the accepted guest loader to authenticated root filesystem and app/config digests; a valid firmware measurement alone does not approve subsequently loaded software. Release secrets only over the channel bound to this evidence, never to a host-provided recipient key. Relaying a genuine guest's report does not prove where it runs or who controls its display.
- Authenticate and encrypt all storage/network I/O outside private guest memory. Start with software rendering inside the guest; shared framebuffers, virtio devices and ordinary GPU passthrough are not confidential I/O. Host-visible shared buffers contain only intended output or authenticated ciphertext. Guest users receive only approved app interfaces, not administrative/debug APIs that export protected secrets; confidential memory cannot compensate for a guest willingly disclosing them. Guest bugs and malicious virtual devices still need hardening; attestation does not prove bug-free runtime behavior.
- Keep epochs, storage-version roots and mutation authority at an online tenant service. Use atomic sequence checks and idempotent operation IDs to reject rolled-back/forked state, and reauthorize resumed sessions before new service operations. Disable migration/snapshot import unless an explicitly reviewed profile preserves these properties. No offline sensitive-data lease in this research option: an attested guest has no automatically trustworthy wall clock, and a host can pause it while it holds secrets. Future server operations can be revoked; deletion of secrets already in a suspended guest is not promised.
- The research track must define the separate execution-evidence schema, fixed verdicts, verifier references and consent-screen coverage before admission; it is currently undefined. **Do not extend or relabel `workspace-measured-host`**. The verifier may see platform identifiers in raw evidence: separate consent, minimal retention and no raw host evidence to tenants remain required. Require current mitigation policy, including evidence for platform fixes that a quote's version fields may not establish. Unsupported or unverifiable mitigation state means unavailable, not acceptance of an old TCB.

This buys confidentiality/integrity of unrendered guest data against some hostile-host attacks that UID separation, measured boot and normal VMs do not address. Costs include limited platform coverage, firmware/reference maintenance, memory/rendering overhead and recovery complexity. Availability, traffic patterns, relevant side channels, guest exploitation and physical attacks outside the vendor threat model remain; displayed output and input still cross the hostile host. No live-data class promotion, offline-expiry guarantee or trusted physical viewer follows. Admission requires end-to-end negative tests for replayed quotes, key substitution, unapproved guest/app code, debug/migration, stale state, pause/resume and insecure device paths.

### Portable FIDO2 keys, witnesses and combinations (proposed options)

Use an enrolled roaming FIDO2 credential for optional broker/render-session step-up: the server challenge commits to tenant, instance, requested audience/action, policy hash and session channel key. Verify the WebAuthn RP/origin, challenge and UP/UV flags; distinguish user presence from user verification. `hmac-secret`/WebAuthn PRF may wrap a local unlock secret when supported, domain-separated per tenant/instance/purpose; neither is universally available. Derived secrets enter client memory during use. Specify spare-key/lost-key recovery, revoke the lost credential and require renewed authentication; recovery must not silently satisfy a stronger assurance requirement. Do not infer clone detection from an authenticator signature counter or non-exportability from every passkey.

A portable key reduces reusable-password theft and theft of a locked laptop when the key is absent. It does not attest the browser/compositor, prevent an infected host using an authorized session, or prove the user saw the action encoded by a challenge. An ordinary touch-only key has no trusted transaction display; UV alone does not fix that. Removing a key does not revoke an extracted wrapping secret or create rollback-resistant offline leases. These distinctions follow [WebAuthn's presence/verification model](https://www.w3.org/TR/webauthn-3/#user-presence). No authenticator becomes mandatory for all T0 access.

Independent witnesses and peer review can corroborate signed releases, approval history and log consistency under DESIGN §10.3's pinned quorum. A social web of trust cannot attest another person's runtime, stop colluding peers or turn self-reported posture into evidence of integrity. Retain provenance and independence assumptions; don't average endorsements into a higher host assurance. Witnesses see checkpoints, not personal host inventory or plaintext evidence.

The strongest generally deployable combination is **remote rendering + scoped/rate-limited backend access + optional FIDO2 step-up + server-applied watermarks + independently witnessed evidence**. A confidential remote renderer can additionally narrow infrastructure trust; a local confidential guest remains a hardware-dependent watch item with the physical-access gap above. Neither combination proves who photographed a screen or recalls observed data. Task-specific remote apps that reveal only necessary fields/results reduce exposure further, at the cost of application integration and loss of general desktop functionality. Trusted external displays/input devices change the endpoint assumption and remain a separately approved architecture, not an upgrade to ordinary T0.

## Workspace protocol

T0 uses a workspace-scoped HTTPS surface with TP/1 envelope/status conventions, **not the TP/1 device channel or device certificate**. Discovery publishes the endpoints and pinned tenant trust root. Registration uses short-lived IdP authentication plus nonce-bound proof of the instance key and local consent; subsequent calls use instance-key-signed requests binding method, path, body hash, audience, nonce and expiry over TLS. The server checks replay, scope and registration state.

Bootstrap binds an authenticated tenant discovery domain to the expected IdP issuer/resource tenant before adopting the initial root; a root merely included in an arbitrary response is not already trusted. Validate TLS and issuer/audience, reject cross-tenant redirects/substitution, show the tenant identity at consent and persist the accepted root. Later root/key rotation follows signed continuity, never silent rediscovery. Bind requests to the canonical request target (including query), registration epoch and unique request ID. State-changing retries with the same ID/body return the recorded result; different bodies are rejected. Registration-key replacement requires old-key proof plus reauthentication, or an explicit recovery flow that revokes the old registration and leases. Unsupported schema/envelope versions fail closed.

| Proposed endpoint | Function |
|---|---|
| `POST /sp1/workspaces/register` | Bind user, resource tenant and instance public key; return instance ID, signed policy/manifest and check-in limits. No host inventory. |
| `POST /sp1/workspaces/<id>/check-in` | Submit signed fixed-schema status deltas and last command receipt; receive signed manifest references and pending command IDs. Default maximum interval 5 minutes including jitter; policy may shorten it. |
| `POST /sp1/workspaces/<id>/leases` | Evaluate policy/evidence and issue or renew a bounded key lease. |
| `POST /sp1/workspaces/<id>/render-sessions` | Authorize an instance-signed render request and issue a short-lived single-use ticket bound to the viewer channel key; remote mode only. |
| `GET /sp1/workspaces/<id>/commands` | Fetch signed, scoped command envelopes; acknowledge results through check-in. |
| `GET /sp1/workspaces/<id>/stream` | Optional authenticated wake-only stream; carries no commands/content; polling remains required. |

Revocation and issuance serialize against the authoritative registration epoch: no new key release or render ticket may commit after its revocation. Publish propagation/freshness bounds for replicas and downstream services; a release authorized before revocation may still arrive afterward. A connected cooperative instance learns commands within the check-in interval plus delivery delay; offline action waits for reconnection or enforceable lease expiry. Report those bounds rather than claiming instantaneous remote wipe.

### Keys and leases

```text
volume DEK → wrapped by independent instance KEK → wrapped by tenant KMS key
```

The release flow below is for local tenant volumes; remote-mode storage keys stay with the renderer/broker and never reach the viewer. The tenant KMS key wraps independently random instance KEKs stored only server-side; the instance KEK wraps that instance volume's DEK. No shared KEK is destroyed for a single-instance wipe. On release, the broker unwraps the instance KEK inside KMS/HSM-backed processing, unwraps the DEK and HPKE-encrypts it to a certified instance recipient key (or a registered software recipient key at unattested assurance). Signing and recipient keys are distinct and registration-bound. Only the workspace unwraps the response locally; working DEKs are memory-only.

A broker-signed lease contains version, tenant/user/instance IDs, recipient-key thumbprint, audience, volume/lineage ID, image and policy hashes, minimum security epoch, lease sequence/counter floor, issued/not-before/expiry times, online/offline scope and the encrypted DEK envelope. Verify the pinned delegated lease-signing key, audience, hashes, epoch and counter before mount. The lease signer is a narrowly scoped KMS-backed delegation under the tenant TUF root, not command authority.

Online-scope leases and their DEK envelopes are memory-only. Only offline-scope leases may be stored: policy-bounded software leases for public/low-risk data at unattested assurance, or TPM-sealed leases at measured assurance. Destroying the server's instance KEK does **not** invalidate a previously released DEK envelope: its recipient can still open it subject to that lease's actual local enforcement. Track outstanding lease bounds; report `future-release-denied`, `offline-exposure-pending` and server/local deletion outcomes separately. No immediate remote crypto-shred claim is valid while any usable lease, key or recovery copy survives. A software lease has no hostile-owner expiry bound.

On an unattested host, persistent work secrets are restricted to encrypted cache, wrapped offline-scope DEK/lease blobs and wrapped keys, alongside the registration/image/audit persistence exceptions listed above; offline enforcement depends on cooperative local time/counters and rollbackable software secrets. Consequently this proposal allows **no sensitive internal offline cache at unattested assurance**, including every host without a TPM. Public low-risk offline data may have a policy-bounded software lease without a hardware guarantee. TPM-backed offline leases seal the recipient secret to an approved signed PCR policy and enforce expiry using TPM clock/reset state plus NV counters; fail closed on uncertain clock continuity or rollback. TPM policy limits **unsealing**, not use of keys already unsealed; root can retain an already released DEK.

**Clock and rollback specification gate:** TPM Clock is not trusted UTC and need not advance while unpowered ([TCG architecture, revision 1.83, §36–37](https://trustedcomputinggroup.org/wp-content/uploads/TPM-2.0-1.83-Part-1-Architecture.pdf)). Bind a signed server-time anchor to attested clock/reset/restart state. `TPM2_PolicyCounterTimer` must enforce the clock deadline, `safe` = YES, and equality of both `resetCount` and `restartCount` to the authorized anchor; host comparisons are insufficient. Owner/platform authorization permits `TPM2_ClockRateAdjust` skew within hardware/profile bounds; set conservative deadlines using the slowest allowed rate, not nominal UTC seconds. Unknown drift bounds make measured offline leases unavailable.

**TPM-only offline leases die on every suspend/resume.** TPM Resume increments `restartCount`, and elapsed time across suspend cannot be established from the TPM alone. Drop working keys on suspend and require fresh online authorization after resume or any power/reset discontinuity. Unsupported suspend paths that do not provide a verifiable continuity break cannot claim this lease capability. Measured-host therefore buys only a bounded continuous-awake offline interval, not an offline laptop sleep/wake workflow; already captured keys remain outside this guarantee.

Bind NV epoch/lease counters into the unseal policy with `PolicyNV` (`TPM2_PolicyNV`), and advance them with crash-safe serialized state transitions. For the shared per-(human, tenant) counter budget, specify how sibling leases are reissued or invalidated on an increment; a changed counter must never leave a less-restrictive policy usable. No measured offline capability ships until reset, suspend/resume, power-loss, bounded clock-rate skew, snapshot rollback, concurrent renewal and counter-exhaustion tests pass. TPM absence still falls back to online access, never a fabricated software expiry guarantee.

### Commands and wipe scope

Commands use DESIGN §10.3's per-tenant TUF root and roles: `admins` threshold signatures for `workspace.lock`, `workspace.wipe` and `workspace.revoke-keys`; `policy` for routine `workspace.refresh`; `timestamp` for freshness. Verify target tenant/instance, ceiling, nonce, expiry, minimum epoch and required transparency inclusion. Server identity/session revocation may independently deny access but does not authorize local or renderer-storage destruction.

**Local mode:** `workspace.lock` saves encrypted state, stops apps, unmounts the volume and drops keys. `workspace.revoke-keys` denies renewals and invalidates the instance's server wrapping record; a cooperative live instance locks. `workspace.wipe` additionally destroys the instance KEK and all recoverable broker/backup copies for that instance and requests local tenant-volume removal. A pending retention/recovery copy means shred is incomplete and must be reported as such. It MUST NOT remotely remove a shared homed user or sibling definitions. Local owner removal may later remove an empty user.

**Remote mode:** `workspace.lock` checkpoints encrypted session state, stops its apps, disconnects all viewer channels, drops working keys and blocks new tickets/reconnects until fresh authorization explicitly clears the lock. `workspace.revoke-keys` additionally retires that instance's session/key grants and wrapping record, denies future releases and reconnects, and revokes its remote application credentials where the backend supports it; it need not delete stored ciphertext. `workspace.wipe` applies those access denials, destroys the targeted instance's keys and recoverable copies, and removes its remote session/storage subject to disclosed retention. It never deletes shared source documents, sibling instances or the endpoint's personal data. Copied backend tokens remain subject to the IdP/resource-server bounds above; captured output cannot be recalled.

The renderer, gateway and key broker verify the same `admins` threshold envelopes, target/ceiling, nonce/expiry, epoch and required payload-log inclusion before executing these remote commands. Record command acceptance, execution, grant revocation, scoped storage/key deletion and retention exceptions in the server audit trail and `AuditEvidence`; each service signs its own scoped receipt and exposes it in viewer action history. Evidence-log outages degrade evidence as above, while required destructive-command inclusion still applies. These checks constrain a conforming service: **DESIGN §10.3's rogue-server protection cannot protect data or keys the renderer already holds**. A compromised renderer can copy/delete that data or lie about deletion outside the command path; signatures and audit do not prove erasure.

Receipts use DESIGN §8.2's shared `WipeOutcome` enum and stage/outcome mapping, without remote-mode aliases: `accepted`/`started` record progress, `future-release-denied` records key/session denial, `offline-exposure-pending` tracks outstanding usable leases/keys, `local-completion-reported` covers endpoint removal, `server-data-deletion-reported` covers renderer storage, and `server-keys-destroyed` covers the broker's declared inventory. Use `incomplete/unknown` for unverified or retention-delayed effects. A remote-only viewer has no local tenant volume to delete and must not report local deletion as remote storage completion. A client signature proves only that the instance reported deletion; even a boot quote is not proof that no copies remain. Key-broker destruction receipts describe the broker's controlled storage and retention inventory. Reconcile local removal, server-key destruction and outstanding leases without collapsing them into a single “wiped” flag. Backup restore must replay revocations before serving requests and must not resurrect a retired registration, old epoch or destroyed wrapping record. Wrapped KEK backups encrypted under a still-live tenant KMS key remain recoverable copies until actually removed or rendered undecryptable; a tombstone alone is access denial, not crypto-shred.

When two encryption layers exist (homed/fscrypt home plus tenant-keyed inner volume), the remote crypto-shred claim covers **only the tenant-keyed volume**, not the outer home. It requires elimination of every usable instance key, lease and recovery copy. It cannot recall plaintext, captured keys, exports or already unsealed secrets. Outer-home deletion alone is not this protocol's remote key-revocation guarantee; distinguish it from DESIGN §8.2's legacy work-user removal.

### TRP-Attested broker API (A-BRK-01)

The owner-controlled broker exposes per-instance `create` (key generation inside the TPM), `certify` (`TPM2_Certify` by a per-tenant AK), nonce-bound `quote`, `seal`, `unseal`, and `counter.read/increment` operations. It binds the recipient key to fresh boot evidence and signed PCR policies without arbitrary tenant TPM commands. No raw TPM device access is delegated. Per-tenant isolation includes a hard default budget of **two 8-byte NV counter indices per (human, tenant)**: one epoch floor and one lease/rollback counter shared by that pair's definitions. No extra indices per definition; slots/updates are rate-limited for NV capacity/endurance. Owners may lower the budget; exhaustion yields unavailable offline capability for classes requiring TPM-backed leases, never downgrade of that class to a software lease. Low-risk software leases are unaffected. Updates across definitions must serialize monotonically; removal cleans up indices only after retiring all affected leases. AKs and sealed objects use broker-managed blobs rather than unbounded persistent TPM handles.

## Immutable workspace lifecycle

1. **Ship a signed OCI digest.** Verify against the pinned tenant TUF root/delegation, provenance/SBOM, minimum epoch, freshness and revocation. A mutable channel/tag resolves to an approved digest, never launch authority.
2. **Launch fresh.** Read-only root, no persistent writable application layer, tmpfs for temporary files/rendered signed policy; only allowlisted encrypted data/settings persist. `noexec` does not stop interpreters executing data.
3. **Evaluate release centrally.** Check registration, signer/digest, policy, epoch, revocation, fixed capability verdicts and evidence as required. Log releases. Without runtime attestation/TEE, a broker cannot prove a root-controlled launcher executes its claimed bits.
4. **Expire/revoke as specified above.** Reimaging replaces app state without deleting the volume. Offboarding revokes sessions/releases and requests scoped lock/wipe; short leases bound cooperative offline exposure.

Plaintext keys/tokens, crash dumps, logs, thumbnails, recent files and print spools must not become persistent host artifacts. Encrypt necessary token caches, disable dumps/plaintext container logging and define safe swap/hibernation before unlock. These are tested cooperative-host requirements, not guarantees against root.

Measured evidence must bind a fresh nonce and workspace key to the verified chain and independently trusted references. An immutable distro name or “Secure Boot enabled” is insufficient: validate signing authorities and signed PCR policies. Claim a filesystem digest only when cryptographically bound to measured boot. Mutable `/etc`, `/var`, user services and post-boot changes remain outside that evidence; measurement never upgrades `separation: none`.

## Screenshots, portals and printing

In bridged mode, work windows reach the personal compositor through the dedicated-UID bridge. Separate-seat mode has its own compositor, isolated buses and the same managed portal/flow restrictions; it must not forward work windows to the personal compositor. ABI 1 MUST publish a minimal allowlist of Wayland globals **and versions**, permitting only tested rendering/input paths. Deny unknown globals and versions by default; additions require ABI review and conformance tests. Deny ext/wlr data-control, screencopy/image-capture, foreign-toplevel enumeration, virtual keyboard, input-method and xdg-foreign protocols unless a specific restricted broker API is separately specified/tested. Test each denied global and prevent raw socket escape. `wp_security_context_v1` tags clients; it does not filter them. Claim support only for tested compositor/version combinations, including GNOME/Mutter and KDE; no assumption that tagging is supported or sufficient.

Filter clipboard, drag/drop, file import/export, open-URI and screencast by tenant/class. The workspace portal backend under the work UID mediates with the bridge (or its isolated compositor in separate-seat mode); never expose personal `$HOME`, session/AT-SPI buses, keyring/agent sockets or broad runtime directories. **No XWayland in the workspace.** IME, device, accessibility and notification paths must follow the contract above.

This can prevent workspace apps capturing personal windows and reduce accidental exports through supported APIs. It cannot promise screenshot blocking: personal-session compromise of the compositor can capture every workspace pixel and keystroke, and root or an external camera can capture too. Watermarks/audit deter; they cannot prevent capture. A dedicated bridge UID protects the filter from direct same-UID tampering, not from the compositor it must trust.

Display-layer obfuscation (temporal flicker, sub-visible or "encrypted" pixel encoding, anti-camera dithering) is not a control: the host composes the plaintext the user perceives, holds any encoding key, and can integrate frames as the eye does. Forensic watermarks, if used, are embedded server-side with server-held keys and opaque identifiers, disclosed at consent, and are never sole attribution evidence. Hardware-protected display paths or trusted external displays remove the host from the trust path and belong to a separately approved tier, not T0.

Watermark IDs are derived deterministically as `HMAC(k_wm[epoch], canonical{tenant_id, render_session_id, hash(instance-signed request), doc digest, policy hash})`, with watermark keys held in an HSM. For document output, bind the document digest. For a live session, no document digest exists: encode an explicit absent value and assign one mark per authorized render connection, held across that connection's frames. Reconnect, policy change or watermark-key epoch change requires a fresh instance-signed render request and render-session ID. This gives session-level attribution only, not document/page/frame provenance; retain the assignment's start/end and policy context without inventing a content digest. Use unique server-generated render IDs and normally record each assignment in a durable local audit transaction before releasing its marked output; log inclusion, witnessing and anchoring follow asynchronously with their actual timing recorded. Evidence outages do not block access: buffer records where possible, report coverage gaps and never claim a pre-release commitment that was not made. There must be no unmarked alternate document/stream endpoint for a resource claiming mandatory marking. Remote rendering applies the mark before any frame reaches the host; a compromised compositor cannot capture a nonexistent pre-mark host frame, but can record, crop, alter or combine marked frames. OCR or manual transcription strips pixel marks entirely from the extracted text. Local document apps may reconstruct unmarked content or capture before a local overlay, so they provide a weaker claim.

Bind the assignment to the instance-signed request and retain both. This exposes inconsistent mappings; it does **not** stop a malicious renderer giving someone else the same valid marked output, or prove that the requester leaked it. Log epoch starts and revocations; mark compromised epochs unreliable without publishing identifying records. Key leakage permits forgery even for committed IDs. Specify detection confidence, false-positive tests and robustness against crop/recompression, camera capture and collusion before claiming forensic usefulness. A mark is a lead, never sole attribution evidence; the instance key/session could have been stolen, and another person could have photographed the screen.

Applications print only to the workspace PDF/virtual printer. Deny, keep encrypted, or audit and forward by IPPS through the tenant tunnel; no host CUPS forwarding exception is permitted in this proposal. Previews/temp PDFs/spools stay encrypted or ephemeral. No direct discovery/printer path; owner network exceptions that permit bypass remove the managed-print verdict. Exported PDFs and physical output leave workspace control. Host capture/hostility defeats local print restrictions.

## Fedora and NixOS implementation notes

**Fedora Atomic first.** Prototype the work user, rootless Podman, encrypted volumes and bridge; test GNOME/KDE separately. Package availability proves no lifecycle or portal support. Measured-host capability depends on **sealed bootc/UKI boot plus cryptographic composefs-digest binding** and independently published reference policies; it is unshipped integration work, not a property of ordinary ostree immutability or a default shim/GRUB/BLS path. Until validated, report `workspace-unattested`.

**NixOS module later.** Declare a **fixed pool of tenant user slots**, nonoverlapping subuid/subgid ranges, services, polkit rules and portal/runtime integration. Do not rely on dynamically appended subid entries surviving declarative activation; tests must cover rebuilds and upgrades. The owner controls host rebuilds; tenant policy controls only workspace artifacts. A flake lock/store path proves no active boundary. **NixOS caps at `workspace-unattested` unless an independently trusted third party builds and signs the closure/boot chain and supplies verified references.** Owner-generated boot keys/references alone are insufficient for measured-host assurance.

Both distros inspect live compatibility locally after upgrades, including host-injected GPU drivers outside the pinned image; send only fixed verdicts. Block incompatible combinations instead of relaxing isolation. Publish minimum tested combinations before ABI 1 conformance; no measured-host claim precedes working boot-to-image verification.

## Multi-tenant rules

The isolation unit is the **resource tenant** that owns the data, including B2B guest access. Each (human, resource tenant) pair has its own work UID, network namespace, identity broker, pinned TUF root and rootless storage. Each instance has independently generated keys/volume; multiple definitions per pair do not imply isolation from that pair's other apps. Personal space is `tenant: none`. Same-UID fallback cannot claim these isolation properties.

Cross-tenant flows default to denial. Transfer needs both source egress and destination ingress permission, mediated/audited. No shared mutable profiles, caches or identity sessions across tenants. V1 uses one resource tenant per app/workspace; multiple identities inside one app are deferred.

A host may have multiple T0 workspace tenants but at most one T1/T2 device tenant. Any device-tenant workspace allowlist is enforced **locally only**, appears on the BYOD consent screen, and MUST NOT report identities of present, blocked or non-allowed tenants to the device tenant (including via rejection diagnostics). T0 tenants receive no general inventory or other tenant names.

The device tenant is in co-resident workspaces' TCB when its core can act as root, even for T1's read-only posture: a compromised root core can read unlocked data. T2 root-authority scripts (`root-full` or `root-restricted`) make this exposure explicit. With separate owner consent, expose only `host_device_tenant: none / read-only / root-capable`; absent consent use `undisclosed` and re-evaluate access. The read-only value describes the agreed authority, not a guarantee against core compromise. Preserve DESIGN's server-side per-tenant CA/KMS/database isolation.
